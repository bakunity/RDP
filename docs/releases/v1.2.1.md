# Hermes RDP v1.2.1 — Complete stabilization tree + release packaging hotfix

Release: https://github.com/bakunity/RDP/releases/tag/v1.2.1

`v1.2.1` — рекомендуемый stable release линии `v1.2.x`.

Он делает две вещи одновременно:

1. публикует **полное согласованное дерево большой stabilization-работы**, подготовленной для `v1.2.0`;
2. исправляет release-packaging ошибку, из-за которой исторический tag `v1.2.0` оказался привязан не к полному проверенному release tree.

Между `v1.1.0` и полным деревом `v1.2.1` накопилось **283 commit’а**: изменения затронули Windows Agent/installer/update/repair, Linux API/controller/database/tunnel code, Telegram UX, сайт, release automation, практически всю основную документацию, durable context/evidence и большой набор новых regression/soak tests.

Это не маленький packaging-only hotfix по фактическому объёму продукта: именно `v1.2.1` является полным опубликованным снимком всей принятой stabilization baseline.

## Почему появился v1.2.1

Release workflow `v1.2.0` вычислял tag target как первый/последний commit, менявший `VERSION`, вместо полного validated HEAD, на котором фактически завершилась подготовка release tree.

В результате GitHub Release `v1.2.0` был создан, но сам tag содержал неполные release metadata и старое состояние части документации/README.

Исторический `v1.2.0` tag намеренно **не переписывается**. Вместо изменения уже опубликованной истории был выпущен `v1.2.1` с полным согласованным tree.

## Большая stabilization baseline

### Recovery и устойчивость transport/control plane

Проверены и доведены до предсказуемого поведения:

- Windows reboot recovery;
- Linux server reboot recovery;
- Windows-side SSH transport loss и автоматический reconnect;
- dedicated Hermes sshd restart recovery;
- controller restart без необходимости ронять существующий SSH/RDP transport;
- repeated reconnect cycles без server-side duplicate/orphan sessions;
- несколько независимых Windows devices одновременно;
- one-device failure isolation при работающем втором RDP-сеансе.

### Найденные soak-time bugs

Во время реальной стабилизации были найдены проблемы, которые не проявлялись в простом happy path.

#### CP-001 — stalled TLS client блокировал HTTPS API acceptance

Один зависший raw/TLS client мог заблокировать глобальный API accept path. Сервис оставался active, но новые health/telemetry requests переставали нормально обрабатываться.

TLS handshake был вынесен в bounded per-connection worker. Live acceptance подтвердил, что параллельные health requests остаются быстрыми даже при намеренно зависшем соединении.

#### CL-001 — desired OFF + local ON мог зациклить reconciliation

Transport-first loop мог не доставить control state, который сам требовался для остановки transport.

Control polling был отделён от transport recovery. Реальный fixture после исправления сходился OFF/ON без искусственного restart или нового command sequence.

#### CU-001 — stale command мог бесконечно показываться как executing

Добавлен deterministic timeout pending command и защита от позднего stale result. Desired state остаётся durable, pending корректно очищается, а устаревший completion не переписывает более новое состояние.

## Windows compatibility

### Windows 10 x64 + 32-bit PowerShell

На реальном Win10 Pro build 19045 был воспроизведён запуск `SysWOW64` PowerShell на 64-битной ОС.

Installer/Repair научились корректно обращаться к native `System32` через `Sysnative`, поэтому используются настоящие Windows `ssh.exe` / `ssh-keygen.exe`, а SYSTEM Scheduled Task получает canonical native path.

Fresh install из x86 PowerShell прошёл live end-to-end: native OpenSSH, Ed25519 identity, `known_hosts`, Scheduled Task, reverse tunnel и Microsoft RDP.

### Windows Server 2019

Исправлен старый ProductType gate, ошибочно блокировавший поддерживаемый Windows Server.

Windows Server 2019 Datacenter прошёл fresh install, update с сохранением identity и реальный RDP через Hermes.

### Existing-install guard

Повторное действие `Добавить ПК` на уже установленной машине больше не выполняет destructive mutation. До фикса этот edge case мог остановить рабочую Scheduled Task ещё до ожидаемой pairing failure.

## Transactional lifecycle

### Linux server update

Updater получил полноценную transaction boundary:

- requested ref → immutable SHA;
- consistent SQLite backup;
- backup app/config/systemd units/metadata;
- bounded post-update health verification;
- automatic rollback при deliberate post-mutation failure.

Live acceptance подтвердил сохранение устройств/endpoints после успешного update и полное восстановление предыдущего runtime после forced failure.

### Windows client update

Windows updater теперь:

- отказывается маскировать unhealthy pre-state под обычное обновление;
- скачивает candidate по immutable SHA;
- парсит PowerShell до остановки runtime;
- сохраняет Agent/Task snapshot;
- ждёт bounded stable runtime;
- автоматически возвращает предыдущий Agent/Task при failure.

При успешном update сохраняются Device ID, `device.json`, private/public key, `known_hosts` и назначенный порт.

### Existing-device Repair

Появился отдельный Repair уже зарегистрированной Windows-машины.

Repair не выполняет fresh pairing/rekey и сохраняет существующую trust/identity boundary. На live fixture были удалены Agent file + Scheduled Task, после чего Repair восстановил runtime с `REPAIR=PASS`.

Отдельный deliberate failure проверил автоматический `ROLLBACK=PASS`.

Если отсутствует критическая identity (`device.json`, private key или `known_hosts`), Repair останавливается и не создаёт скрыто новую машину.

## RDP performance / telemetry

Во время обычной работы был найден заметный performance regression: тяжёлые NetTCPIP/WMI/process probes запускались слишком часто в telemetry loop и совпадали с наблюдаемыми RDP micro-freeze.

Fast path был переработан:

- heavy NetTCPIP/WMI operations убраны из ordinary cadence;
- resource/heavy telemetry выполняется реже;
- bounded observation mode временно повышает частоту только по запросу;
- cached SSH/process/RDP fast snapshot выполняется за десятки миллисекунд.

После оптимизации пользователь подтвердил плавную обычную работу через Hermes RDP без прежних заметных микрофризов.

## Multi-device и endpoint lifecycle

Live проверено:

- несколько independent reverse SSH tunnels одновременно;
- постоянный отдельный endpoint/порт для каждого device;
- два Microsoft RDP-сеанса к разным Hermes devices одновременно;
- failure/OFF одного устройства не нарушает второе;
- hard delete закрывает listener, отзывает API/SSH authorization и освобождает порт;
- освобождённый порт безопасно переиспользуется новым fresh pairing.

## Telegram control и UX

### Control behavior

- `OFF` закрывает публичный listener и прерывает Hermes RDP access;
- `ON` восстанавливает tunnel/listener;
- `RESTART` заменяет SSH transport и возвращает ровно один tunnel;
- agent heartbeat остаётся независимым от access state;
- desired/applied/tunnel state отображаются раздельно;
- публичный endpoint status определяется server-side listener truth.

### Dashboard / mobile

- command/tunnel state автоматически обновляется после действий;
- больше не требуется постоянный ручной Refresh;
- OFF и RESTART получили нормальный full-width mobile layout;
- добавлена кнопка **ВОССТАНОВИТЬ КЛИЕНТ**;
- добавлена **НОВЫЙ КОД** для детерминированного retry pairing UX.

## Security boundaries

Стабилизация сохранила OpenSSH security model:

- отдельный Ed25519 identity на каждый Windows ПК;
- private key остаётся на endpoint;
- cross-device SSH authorization запрещён;
- admin SSH `:22` и Hermes tunnel sshd `:7000` изолированы;
- OFF/DELETE закрывают активный public listener;
- Hermes не добавляет Defender exclusions и не требует отключения Defender;
- real-time Defender coexistence проверена на рабочем fixture.
