# Hermes RDP v1.2.0 — Stabilization, recovery & compatibility

Release: https://github.com/bakunity/RDP/releases/tag/v1.2.0

`v1.2.0` — большой стабилизационный релиз после перехода Hermes RDP с FRP на системный OpenSSH в `v1.1.0`.

Главная задача этой версии была не добавить ещё один транспорт, а довести существующую архитектуру до состояния, в котором она предсказуемо переживает реальные Windows/Linux сбои, несколько устройств, reboot/reconnect, ошибки обновления и восстановление существующего клиента.

> **Важно про опубликованный tag:** у первоначального `v1.2.0` была обнаружена ошибка release packaging: workflow привязал tag не к полному проверенному release tree. Исторический tag не переписывается. Полное согласованное дерево этой стабилизационной линии опубликовано как **`v1.2.1`**, и именно его рекомендуется использовать для install/update.

## Главное в v1.2.0

- полноценный **Repair существующего Windows-клиента** без fresh pairing и без смены device identity;
- **transactional server update** с consistent SQLite backup, backup конфигурации/units и автоматическим rollback;
- **transactional Windows update** с сохранением device ID, SSH identity, `known_hosts`, порта и Scheduled Task;
- поддержка **Windows Server 2019**;
- исправлена работа на **Windows 10 x64 из 32-битного PowerShell** через `Sysnative` и native OpenSSH;
- подтверждена работа **нескольких Windows-ПК одновременно** с независимыми endpoint;
- закрыты control-plane deadlock/stale-command проблемы, найденные во время soak-тестов;
- сильно облегчён обычный telemetry path, который вызывал заметные RDP micro-freeze;
- Telegram dashboard получил автоматическое обновление состояний, нормальный mobile layout, Repair и выдачу нового pairing-кода;
- документация, публичный сайт, testing guide и validated-scenarios были синхронизированы с реально принятой архитектурой.

## Надёжность и recovery

В ходе стабилизации были не только добавлены recovery-механизмы, но и реально проверены аварийные сценарии:

- Windows reboot → Agent и reverse SSH tunnel восстанавливаются автоматически;
- Linux server reboot → controller/sshd возвращаются, Windows agents переподключаются;
- временная потеря Windows-side SSH transport → создаётся новый tunnel без повторного pairing;
- restart controller не должен ронять уже работающий RDP transport;
- restart dedicated Hermes sshd приводит к автоматическому reconnect клиентов;
- repeated sshd reconnect cycles не оставляют server-side duplicate/orphan sessions;
- несколько устройств держат независимые reverse SSH tunnels одновременно;
- отключение/сбой одного устройства не нарушает работу другого активного RDP-сеанса.

## Control plane: найденные и закрытые баги

Soak-тесты выявили несколько проблем, которые были трудно заметны в обычном happy-path тестировании.

### Stalled TLS client мог блокировать API

Один зависший TLS-клиент мог занять глобальный accept path HTTPS API: сервис оставался `active`, listener существовал, но health/telemetry переставали нормально обслуживаться.

Исправление перенесло TLS handshake в bounded per-connection worker. После фикса пять параллельных `/healthz` запросов проходили, пока отдельный raw TCP client намеренно оставался зависшим.

### Desired OFF мог конфликтовать с локальным ON

Старый transport-first loop мог застрять в ситуации, когда server desired state уже `OFF`, локальный state ещё `ON`, а SSH transport не поднимается. В результате control/telemetry не доходили до состояния, которое само должно было выключить transport.

Control poll был отделён от transport reconciliation. Реальный Windows fixture затем сходился в OFF и обратно в ON без изменения command sequence.

### Команда могла оставаться «выполняется» бесконечно

Добавлен deterministic command timeout. Desired state сохраняется, pending очищается, а поздний stale result больше не может переписать уже завершившееся/timeout состояние.

## Windows compatibility

### Windows 10 x64 + PowerShell x86

На реальном Windows 10 Pro x64 был воспроизведён запуск из `SysWOW64` PowerShell (`Is64BitOS=True`, `Is64BitProcess=False`). Из-за WOW64 filesystem redirection обычный `System32\OpenSSH` path мог вести не туда.

Installer/Repair теперь используют `Sysnative` для доступа к native `ssh.exe` / `ssh-keygen.exe`, сохраняя canonical System32 path для SYSTEM Scheduled Task.

Fresh install из 32-битного PowerShell был принят live: OpenSSH, task, keypair, `known_hosts`, reverse tunnel и реальный Microsoft RDP прошли end-to-end.

### Windows Server

Старый ProductType gate ошибочно отклонял поддерживаемый Windows Server. Это было воспроизведено и исправлено.

Windows Server 2019 Datacenter затем прошёл fresh install, update с сохранением identity и полноценный RDP через Hermes.

### Защита существующей установки

Повторное `Добавить ПК` на уже корректно установленной машине больше не выполняет destructive actions. До фикса такой путь мог остановить рабочую Scheduled Task ещё до ожидаемой pairing-ошибки.

## Transactional Update

### Linux server

Server updater теперь:

- разрешает requested ref в immutable commit SHA;
- создаёт consistent SQLite backup до mutation;
- сохраняет app/config/systemd state и metadata;
- имеет bounded health gate;
- автоматически восстанавливает предыдущий runtime при deliberate post-mutation failure.

Успешный update сохраняет зарегистрированные устройства и их endpoints.

### Windows client

Windows updater:

- проверяет pre-state и не пытается маскировать сломанную установку под обычный update;
- скачивает candidate по immutable SHA;
- парсит PowerShell до остановки рабочего runtime;
- сохраняет Agent/Task snapshot;
- после активации ждёт bounded stable runtime;
- при deliberate failure восстанавливает предыдущий Agent и Scheduled Task.

Live acceptance подтвердил сохранение `device.json`, private/public SSH key, `known_hosts`, Device ID и назначенного RDP-порта.

## Existing-device Repair

Добавлен отдельный Repair flow для уже зарегистрированной машины.

Repair намеренно **не** делает fresh pairing и не создаёт новый device. Он сохраняет:

- Device ID;
- API token;
- Ed25519 identity;
- `known_hosts` trust anchor;
- назначенный внешний RDP-порт.

На live fixture удалённые Agent file + Scheduled Task были восстановлены с `REPAIR=PASS`.

Отдельно проверен forced-failure path: после candidate mutation продукт вернул `ROLLBACK=PASS` и восстановил предыдущий Agent/Task snapshot.

Если потеряны `device.json`, private key или `known_hosts`, обычный Repair специально останавливается вместо скрытого re-pair/rekey.

## Performance: устранение RDP micro-freeze

Во время реальной работы был найден performance regression: тяжёлые WMI/NetTCPIP/process операции выполнялись слишком часто в 3-секундном telemetry loop и могли занимать значительную часть интервала.

Из ordinary fast path убраны тяжёлые probes. Ресурсная/heavy telemetry вынесена на более редкую cadence и bounded observation mode.

На принятом Agent fast core измерялся в **десятках миллисекунд**, а пользователь подтвердил, что обычная работа через Hermes RDP снова стала плавной без прежних заметных микрофризов.

## Multi-device и endpoint lifecycle

Проверено:

- несколько Windows devices одновременно;
- отдельный постоянный RDP endpoint на каждое устройство;
- два Microsoft RDP-сеанса к разным Hermes devices одновременно;
- one-device failure isolation;
- hard delete отзывает API token/public key и закрывает listener;
- удаление освобождает порт;
- освобождённый порт безопасно выдаётся следующему fresh pairing.

## Telegram UX и server-authoritative state

Telegram control в этом релизе стал заметно надёжнее:

- `OFF` закрывает публичный listener и обрывает Hermes RDP access;
- `ON` восстанавливает tunnel/listener;
- `RESTART` заменяет SSH transport и возвращает ровно один tunnel;
- dashboard разделяет desired/applied/tunnel state;
- endpoint truth берётся с Linux listener, а не из потенциально ложного Windows-side признака;
- состояние обновляется автоматически без обязательной кнопки Refresh;
- OFF/RESTART получили нормальный mobile layout;
- добавлена кнопка **ВОССТАНОВИТЬ КЛИЕНТ**;
- кнопка **НОВЫЙ КОД** создаёт новый pairing code и обновляет installer command.

## Security boundaries

Стабилизация не ослабляет базовую OpenSSH security model `v1.1.0`:

- у каждого устройства собственный Ed25519 identity;
- private key остаётся только на Windows;
- cross-device SSH authorization не разрешён;
- admin SSH `:22` отделён от Hermes tunnel sshd `:7000`;
- Hermes не добавляет Microsoft Defender exclusions и не требует отключать Defender;
- Defender real-time protection был проверен на acceptance fixture вместе с работающим Hermes RDP.
