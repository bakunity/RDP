`v1.1.0` уже действительно опубликован как последний GitHub Release — документация в одном месте сейчас ошибочно говорит, что тег ещё «ожидает публикации».

# 2. Что происходит с ON/OFF и почему сейчас всё выглядит непонятно

Вот здесь действительно есть архитектурная путаница интерфейса.

Сейчас `ONLINE` вообще **не означает, что RDP-доступ включён**.

Бот считает ПК ONLINE только по heartbeat: если Windows-агент недавно прислал телеметрию — ПК зелёный. Поэтому после `OFF` компьютер совершенно правильно продолжает показываться:

```
🟢 OSIO · ONLINE

```

Потому что агент должен продолжать работать. Иначе после OFF мы вообще не смогли бы отправить ему ON.

Но интерфейс этого не объясняет.

Фактически у нас сейчас есть **пять разных состояний**, которые UI свалил почти в одно:

```
1. Windows Agent     ONLINE / OFFLINE
2. Желаемый доступ   ON / OFF
3. SSH tunnel        CONNECTED / DISCONNECTED
4. Public endpoint   OPEN / CLOSED
5. RDP session       ACTIVE / NONE

```

Это и есть одна из главных вещей, которые надо исправить.

# 3. Почему написано «SSH-туннель: остановлен», хотя всё работает

Вот это уже похоже на настоящий дефект telemetry.

Windows-агент сейчас определяет SSH-туннель не просто по наличию `ssh.exe`. Он ищет процесс, в command line которого одновременно должны буквально присутствовать:

```
путь к конкретному SSH private key

```

и

```
0.0.0.0:<PORT>:127.0.0.1:3389

```

Только тогда:

```
ssh_tunnel_running = $true

```

При этом установщик проверяет успешный запуск **мягче**: ему достаточно найти `ssh.exe`, содержащий путь к ключу.

Получается неприятная ситуация:

```
Installer:
ssh.exe + наш key
        ↓
     RUNNING ✅

Agent telemetry:
ssh.exe + наш key + точное совпадение -R
        ↓
    NOT FOUND ❌

```

Это очень хороший кандидат на причину твоего:

```
SSH-туннель: остановлен
Endpoint: доступен
RDP работает

```

Но окончательно причиной я бы его назвал только после проверки реального `CommandLine` процесса на тестовой Windows.

Есть и второй возможный сценарий: **старый/orphan SSH-процесс продолжает держать порт, а новый агент его не распознаёт**.

То есть поле `SSH-туннель` сейчас я бы вообще не считал достоверным.

# 4. После OFF проблема серьёзнее

Есть ещё один момент.

Сразу после OFF один старый кадр telemetry допустим: Windows сначала собирает telemetry, отправляет её серверу и только в ответ получает pending command. После этого выполняет OFF. Это видно в цикле агента.

Но спустя заметное время должно стать:

```
Доступ: OFF
SSH: disconnected
Endpoint: closed
RDP: 0

```

А у тебя всё ещё:

```
Endpoint: доступен
RDP-соединений: 1

```

Поэтому это уже надо включить в блокирующий тест.

Причин потенциально три:

```
Telegram OFF
    │
    ├── команда не выполнилась
    │
    ├── Windows выполнила её, но не нашла ssh.exe
    │
    └── server close helper не закрыл sshd listener

```

И сейчас самое плохое то, что **Telegram не показывает, какой из вариантов произошёл**.

Хотя база уже умеет это хранить.

SQLite содержит:

```
enabled
pending_command
pending_created_at
last_result_json
command_seq

```

А после выполнения Windows отправляет:

```
ok
message
completed_at

```

То есть backend уже почти готов к нормальному UX — Telegram просто пока не использует эту информацию.

# 8. «Внешние клиенты: 127.0.0.1» тоже надо исправлять

Это поле сейчас вводит в заблуждение.

Windows смотрит подключения к своему локальному:

```
127.0.0.1:3389

```

Но reverse SSH приходит к RDP локально через SSH. Поэтому Windows вполне может видеть source:

```
127.0.0.1

```

вместо настоящего внешнего клиента.

Я бы в нынешнем виде это поле убрал.

А если нам действительно нужны:

```
Внешние клиенты
IP
география
время подключения

```

это надо определять **на Hermes server до SSH forwarding**, а не на Windows.

# 9. Серверное отключение туннеля тоже надо протестировать живьём

При OFF бот сейчас не только отправляет команду Windows, но и пытается немедленно закрыть listener на сервере.

Helper ищет PID listener и завершает его только тогда, когда `/proc/PID/exe` совпадает с:

```
/usr/sbin/sshd

```

А тест сейчас проверяет фактически только то, что эта логика присутствует в скрипте. Он не поднимает настоящий OpenSSH reverse tunnel и не проверяет реальный child sshd.

Поэтому в стабильной версии нужен настоящий integration test:

```
поднять SSH
→ порт OPEN
→ OFF
→ sshd child умер
→ порт CLOSED
→ ON
→ новый child
→ порт OPEN

```

# 12. Обновление и rollback пока не уровня stable

Server updater делает backup, обновляет файлы и перезапускает сервисы. Но если новый сервис после обновления не стартовал, автоматического восстановления предыдущего состояния сейчас нет.

Windows updater ещё проще: сохраняет старый agent и откатывает его при parse error, но не при runtime-проблеме нового агента или невозможности восстановить tunnel.

Для стабильного продукта нужно:

```
backup
→ update
→ health check
→ tunnel check
→ success

              или

backup
→ update
→ FAIL
→ automatic rollback
→ previous version restored

```

# 17. Какой вектор проекта я бы зафиксировал

**Hermes RDP — самостоятельная система удалённого доступа к нескольким Windows-компьютерам через один публичный Linux-сервер, с безопасной автоматической регистрацией устройств, постоянными адресами, мониторингом и управлением из Telegram.**

Не «SSH-wrapper».

Не «скрипт для проброса RDP».

Не «FRP replacement».

А именно небольшой self-hosted **remote access control plane**.

И это важный поворот в позиционировании.

# 19. Что осталось до готового продукта

Я бы теперь **заморозил добавление новых фич** и прошёл 5 этапов.

### Этап 1 — Control Plane Correctness

Самый высокий приоритет.

Исправить:

- достоверное определение SSH;
- OFF/ON/RESTART lifecycle;
- server-side listener detection;
- desired state / actual state;
- pending/result/error;
- command timeout;
- orphan SSH processes;
- truthful Telegram state;
- правильную семантику ONLINE.

Результат:

> Когда Telegram пишет `Доступ выключен`, порт действительно закрыт. Когда пишет `SSH connected`, SSH действительно подключён.

---

### Этап 2 — Reliability

Закрыть:

- Windows reboot;
- network disconnect/reconnect;
- server reboot;
- controller restart;
- второй/третий ПК;
- DELETE;
- port reuse;
- повторную установку поверх старой версии;
- legacy ACL;
- update;
- automatic rollback.

---

### Этап 3 — Telegram UX

После того как состояния станут достоверными:

# 21. Что должно считаться готовым Hermes RDP

Готовый продукт для меня выглядит так:

> Ставишь Hermes на чистый Debian/Ubuntu одним стабильным install flow. Открываешь Telegram. Нажимаешь «Добавить ПК». Вставляешь одну команду в PowerShell. Компьютер появляется в панели, получает собственный адрес и после этого переживает перезагрузки и обрывы сети самостоятельно.

И дальше:

```
ПК может быть ONLINE, но доступ OFF — это понятно.

ON действительно открывает endpoint.
OFF действительно его закрывает.
RESTART действительно пересоздаёт туннель.

Любая команда показывает:
отправлена → выполняется → выполнена / ошибка.

У каждого ПК:
свой ключ
свой token
свой порт
своё состояние

Удаление действительно отзывает доступ.

Обновление не может оставить систему поломанной:
либо новая версия здорова,
либо автоматический rollback.

README, документация, сайт и release
описывают одну и ту же архитектуру
и одну и ту же стабильную версию.

```

Вот тогда это уже не «проект, который заработал», а **законченный self-hosted продукт**.

И самое важное сейчас: **не трогать сайт и не наращивать новые возможности, пока не приведём control state к истине**. У нас уже есть работающий транспорт. Следующий этап должен превратить его в предсказуемую систему. После этого уже имеет смысл делать красивую документацию и сайт вокруг действительно зафиксированного поведения. 👨‍💻🔥
