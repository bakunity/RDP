# Hermes RDP v1.2.0 — draft

Статус: **черновик стабилизационного релиза**. Этот файл ведётся по мере прохождения PR/acceptance и не является опубликованным release note до финального merge/tag.

## Уже подтверждено

- OpenSSH остаётся транспортом Windows-клиентов; FRP не возвращается в runtime-архитектуру.
- Windows 10 x64 + PowerShell x86: подтверждена необходимость `Sysnative` для native Microsoft OpenSSH; installer resolver и regression coverage добавлены.
- Повторный `Добавить ПК` на уже установленной Hermes-машине больше не выполняет destructive actions: existing-install guard срабатывает раньше остановки Task/SSH и backup flow.
- Desired access и queued command меняются атомарно в SQLite.
- Dashboard разделяет heartbeat агента, желаемый доступ, применённое состояние агента, SSH-транспорт и публичный RDP endpoint.
- Public endpoint truth перенесён на Linux-сервер: listener определяется по `/proc/net/tcp*`; Windows self-probe удалён.
- RDP-сессии разделены на Hermes и прямые LAN/VPN подключения.
- Live acceptance на MIPC:
  - прямой RDP: `Hermes=0`, `LAN/VPN=1` — PASS;
  - RDP через Hermes: `Hermes=1`, `LAN/VPN=0` — PASS.
- Пользовательские статусы dashboard русифицированы.

## Performance stabilization — IMPLEMENTED, NOT YET LIVE VALIDATED

На реальной Windows-машине до фикса измерено:

```text
Get-NetTCPConnection -State Established        ≈ 1059 ms
Get-NetTCPConnection -LocalPort 3389           ≈ 516 ms
Get-CimInstance Win32_Process                  ≈ 357 ms
Get-TopProcesses sampling window               = 800 ms минимум
```

Это подтвердило performance regression: 3-секундный telemetry loop выполнял слишком много тяжёлых операций и мог занимать большую часть интервала, что совпало с наблюдаемыми микрофризами RDP.

Реализовано:

- 3 сек: heartbeat/commands, access, SSH, RDP-channel state;
- 15 сек в фоне: CPU/RAM/disk/network/sessions/route/uptime;
- при активном наблюдении resources обновляются каждые 3 сек;
- TOP processes не собираются в фоне;
- TOP processes собираются раз в 6 сек только во время явного режима наблюдения;
- `НАБЛЮДАТЬ 60с` автоматически выключается через минуту;
- после истечения lease Telegram прекращает 3-секундное авто-редактирование dashboard;
- full `Get-NetTCPConnection -State Established` удалён: RDP query ограничен local port `3389`, peer query выполняется только для loopback RDP;
- `Get-SshProcesses` фильтрует `Win32_Process` сразу по `ssh.exe`, а результат повторно используется в текущем telemetry cycle;
- API отдаёт выбранному Windows agent `telemetry_live=true` только пока открыт его device view и действует 60-секундный lease.

Нужно live-проверить на MIPC:

- timing нового фонового цикла;
- отсутствие/снижение RDP микрофризов;
- `НАБЛЮДАТЬ 60с` -> heavy telemetry включается;
- через 60 сек -> heavy telemetry и автообновление выключаются.

## Windows Server support — IMPLEMENTED, NOT YET LIVE VALIDATED

Подтверждённый installer bug: прежняя проверка `ProductType != 1` запрещала Windows Server ещё до следующей проверки Caption, хотя `Server` был указан как допустимый вариант.

Исправлено:

- Windows client `ProductType=1`: допускаются Pro / Enterprise / Education;
- Windows Server `ProductType=2/3`: допускаются распознанные Windows Server editions;
- blanket error `Установщик предназначен для клиентской Windows` удалён;
- post-install `ssh.exe` lookup также ограничен фильтром `Name='ssh.exe'`;
- добавлен regression test Windows Server product type.

Нужно пройти реальную fresh-install проверку на Windows Server.
